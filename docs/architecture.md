# Architecture conventions

Use C++ for stable foundations, reusable logic, integration, and behavior that benefits from native debugging or performance. Blueprint children can configure C++ parents and implement presentation and appropriate event behavior. Choose the boundary for the feature; avoid a C++-only rule. Keep related code cohesive inside the existing runtime module until a real dependency or loading boundary justifies another Unreal module. [Epic: C++ and Blueprint](https://dev.epicgames.com/documentation/unreal-engine/coding-in-unreal-engine-blueprint-vs-cplusplus)

For persistent strong references to reflected UObject members, use `UPROPERTY()` with `TObjectPtr<T>`. An unreflected `TObjectPtr` alone does not protect lifetime. Use `TWeakObjectPtr` for non-owning references that may expire, and `TSoftObjectPtr` for asset references that should support deferred loading. Raw pointers remain appropriate for short-lived locals and parameters when lifetime is established; validate references at use boundaries. [Epic: object pointers](https://dev.epicgames.com/documentation/en-us/unreal-engine/object-pointers-in-unreal-engine)

Expose purposeful tuning and configuration properties with suitable edit permissions, categories, tooltips, units, and editor ranges. Prefer limited access such as `EditDefaultsOnly` or `BlueprintReadOnly` where appropriate. Enforce invariants in runtime code too: metadata clamps only guide the editor and are not runtime validation. [Epic: metadata specifiers](https://dev.epicgames.com/documentation/en-us/unreal-engine/metadata-specifiers-in-unreal-engine)

Choose delegate features separately. Native versus dynamic concerns reflection, Blueprint access, serialization, and overhead; single-cast versus multicast concerns listener count. Multiple listeners alone do not require a dynamic delegate. Specify subscription ownership and unbinding when adding listeners, and avoid a global event bus without concrete requirements. [Epic: delegates](https://dev.epicgames.com/documentation/en-us/unreal-engine/delegates-and-lambda-functions-in-unreal-engine)

The boilerplate supplies infrastructure and a sandbox fixture. Add controllers, UI, navigation, networking, materials, or gameplay frameworks when an approved slice needs them. Do not rename internal Unreal identifiers as part of routine feature work; module/package renames require a separate migration.

## Expedition persistence

`FCombatBattle::Restore` and `FExpeditionRun::Restore` validate detached values before installing them. Restore never calls Start/NewRun, generates offers, rolls initiative or spends RNG. Combat validation checks bounded stats, grid/occupancy, life/HP/deadline consistency, enum values, initiative/order/active actor and budgets. Run validation checks selected catalog profiles and recipe facts, phase/completion/history/offer relationships, one camp, artifact state and reward-derived equipment/consumable allowances. This is coherent bounded-state validation, not a replay proof or tamper-proof format.

`FExpeditionSave` encodes version 4 value-only JSON (versions 1–3 are rejected as unsupported) with required fields and exact types, then validates the complete document. `FExpeditionSession` owns the live run for the player adapter. Every accepted party command, whole enemy turn, route, reward, recovery and new run is evaluated on a candidate. The candidate and any deduplicated ending record are written together before installation. A write failure rejects the candidate, including its random progression and deaths. Save is an explicit confirmation of this same checkpoint; Resume reads the latest committed file. There is no stale backup fallback. Presentation only submits session commands and observes const run queries.

The local file adapter writes a sibling `.pending` file. On Linux and macOS it replaces the destination with a same-directory rename. If that rename fails while the old file exists, the Linux build moves the old checkpoint aside to `.previous`, installs the new file, and restores the old one on failure. On Windows the same `.pending` file is installed with one `MoveFileExW(MOVEFILE_REPLACE_EXISTING | MOVEFILE_WRITE_THROUGH)` call (write-through is best-effort, not a durability guarantee), so the prior checkpoint is never absent; if a non-replacing fallback cannot restore the prior file, the error names the `.previous` path instead of claiming it was retained. A failed write/rename preserves the prior valid checkpoint and history. The adapter does not promise fsync/power-loss durability, cloud sync, multiple writers or migration across save versions/platforms. A stale live session is rejected if its current value differs from the disk checkpoint. Startup does not write a run. Records contain identity, seed, outcome, victories and survivors/summary; they never enter party construction or power calculations.

Fresh runs use one GUID at construction. The seed remains the reproducible gameplay input; tests can supply an explicit run identity. Loading retains that identity. Default storage is `FPaths::ProjectSavedDir()/SaveGames/Expedition/current-v1.json`; native validation can select an isolated directory through `-ExpeditionSaveRoot=<directory>` or `EXPEDITION_SAVE_ROOT`. No reflected UObject or presentation selection/camera value enters a save.

A packaged Linux Development game resolves that default under `~/.config/Epic/DnDDiceRoll/Saved/`. (The earlier sandboxed Mac app used `~/Library/Containers/com.YourCompany.DnDDiceRoll/…`, where overrides outside its sandbox could be unreadable.) Native fixtures must use an owned directory the game can access. The editor's default remains the project's `Saved/` directory.

NewRun also enforces unfinished-run protection at the session boundary, including a saved run not yet resumed after startup. An explicit startup NewRun can recover an unreadable/incompatible file by moving it to a unique sibling `.unreadable-…` path; its bytes remain preserved, even if writing the replacement fails. The optional preserved-path result drives visible recovery feedback. Resume never accepts or repairs invalid data, and an active session never quarantines its checkpoint. This is recovery from an unreadable document, not an older-save fallback or migration.

`FExpeditionSession::Close()` (Return to menu, #132) only drops the live run from memory: it writes, moves or deletes nothing, so the checkpoint stays as last committed, Resume restores it and NewRun's unfinished-run protection still applies. `HasUnfinishedCheckpoint()` is the matching read-only query (a readable, unfinished checkpoint) that lets the start screen focus Resume.

## Expedition presentation

The rules settle each command instantly and return an `FCombatResult` with presentation facts: actor, target, the path walked, every damage or healing die in roll order, and who was newly downed or killed. Rules never read these back. `FCombatBattle::Forecast`, `PathTo` and `ActionReach` (reach and blocked-sight cells, independent of budgets and eligibility) are const queries that share resolution tuning and consume no random numbers. The controller's `ShowsTargeting()` is the one gate for targeting feedback (reach markers, target chips, board highlights): a party member has the turn in a fight, no overlay is open and no playback is running. The HUD reads the controller's reach and targets for the frame instead of recomputing them.

`FExpeditionPlayback` (plain C++) replays committed results as timed steps and owns only display state: unit positions, displayed HP, floating text, projectiles, the dice tray and turn banners. `Finish` completes every queued step silently and always converges on the committed snapshot. An accepted player command finishes earlier playback before its own plays; rejected input leaves playback alone. Resume, new runs and route changes rebuild and reset it; loot and camp sync the display after committing; Save changes no state. Animation therefore never delays, reorders or duplicates an outcome. Enemy turns start only when playback is idle.

`AExpeditionBattleView` maps the playback onto runtime primitives (themed scenery per route, character figures, markers, effects, lights, camera) and plays synthesized cues. `AExpeditionPlayerController` turns input into commands for the active adventurer. `AExpeditionHUD` draws the Canvas interface in a 1280-wide design space and registers clickable buttons while drawing. `Project.Tools.CaptureFixtures` writes real checkpoints for each expedition phase under `Saved/CaptureFixtures/` for visual QA; launch with `-ExpeditionSaveRoot=<fixture folder>` and resume.

### Board metric (#141)

`FBoardMetric` (`Presentation/BoardMetric.h`) is the one presentation metric of a battle board: cell size in cm (default 150, a true 5 ft cell), figure height (default 180 cm), and from the cell the board top and the pointer plane. `AExpeditionBattleView` owns it and reads it from `UDiceRollTheme::CellSize` and `FigureHeight`; the primitive fallback uses the same defaults. `CellPosition`, `BoardPosition`, `CursorCell`/`CellAtRay`, camera focus and distance, markers, the targeting overlay and chips, projectiles, effects and playback hop heights all go through it; no other file may hold a cell size. Positions are relative to the view actor.

The r001 art, the camera framing and the poses were authored for a 110 cm cell (`ReferenceCellCm`). Scenery (world, tiles, obstacles, decor, markers, projectiles, effects) lives under a root scaled by `Scale()` = cell / 110 and is written in those reference units, so today's art still fits the board. Unit rigs scale the same way (bases and rings grow with the cell) and their bodies are fitted to the figure height. Camera distances, the zoom clamp (900 to 6400) and capture pose distances stay in reference units; the camera multiplies them by `Scale()`. The default zoom is solved, not approximated: `ExpeditionCameraRig::FitDistance` projects the four board corners (at the board top) through the real camera pose and the HUD-safe rect (`ExpeditionLayout::BoardBounds`, shared with the HUD layout; the HUD feeds the viewport to the view each frame) and returns the nearest distance that contains them. Unreal keeps the vertical FOV of a 16:9 view at any viewport (MaintainYFOV), so ultra-wide screens see more width. The home-yaw fit anchors the pitch ramp; orbiting from the default zoom refits the board for each new yaw (a long board needs more distance end-on than side-on) while a zoom the player chose is kept; `ExpeditionLayout::BoardBounds` also keeps the board clear of the tallest combat log (`ExpeditionLayout::LogRect`, shared with `DrawLog`); the active-unit lean may only use the slack inside the safe rect at the default zoom. Metrics never enter rules, generation, saves or checkpoints (ADR-0001).

### Battle camera and lighting (#143)

`Presentation/CameraRig.h` holds the camera math as pure functions (distances in reference units, so `FBoardMetric` scales them): field of view 40; pitch from zoom, 35 degrees at 1300, 45 at the board's framed distance and 60 at `FarStop(anchor)` (1.4 x the home-yaw framed distance, at least 3000, at most the zoom maximum), linear between and clamped; and a pan focus clamped to the cell-centre box plus two cells. The framed distance fits the board into the screen area the HUD leaves free (`FSafeRect`, a parameter until the HUD layout settles), and the same rectangle slides the view so the focus lands in the middle of that area. Pan comes from Shift+W/A/S/D and middle-drag (plain A stays attack mode) and returns to the active unit when the turn changes. The tabletop overview keeps its own fixed camera, field of view 50.

The key light casts cascaded shadows (4 cascades, 7000 reference cm). Of the flame lights, the two nearest the board centre (ties to the earlier light) cast shadows; all others, and every effect, stay unshadowed. Light attenuation radii are authored in reference cm and scaled by the metric in `MakeLight`. No Lumen, no virtual shadow maps.

### Contextual grid and footprint rings (#142)

Themed battle boards place no per-cell tile meshes: the world's flat ground is the playing surface (at board top), and `Presentation/BoardOverlay.h` draws the grid on it only while it carries meaning. `BoardOverlay::FMask` is a per-cell state mask (Move, Reach, Obstructed, Path, Hover, Victim bits) built each frame from `FBoardHighlights`, which the controller fills from the same rules queries #50 uses (`LegalMoves`, `ActionReach`, `PathTo`, `LegalTargets`, `Forecast`). `BoardOverlay::BuildBars` turns the mask into thin bars in cell units (reach contour runs with exact cardinal corners, corner ticks at lattice vertices inside reach, blocked-sight crosses, the path ribbon with a cost tick per step and a destination bracket, hover brackets, victim frames and, while Alt is held, the whole-board lines). The view draws one `UInstancedStaticMeshComponent` per style on the board plane through `FBoardMetric`; bars are rebuilt only when the mask, path, origin or key changes, and an unchanged frame neither builds a mask nor allocates (inputs are compared against reused scratch storage). This was chosen over a mask texture plus a distance-field floor material because it needs no texture, no per-frame texture upload and no custom shader: the only asset is the small translucent `M_BoardOverlay` ("Color" and "Opacity"), created by `Content/Python/create_board_overlay_material.py`. Without it the bars draw as dimmed opaque lines. The mask is also kept on primitive boards (tests read it), but only themed boards draw it; primitive boards keep tinted cube tiles and the HUD dots. The HUD still counts reach markers per cell and labels path length, AREA victims and chips, so #50's semantics are unchanged.

In the themed look only, figures stand on hollow footprint rings (`FBoardMetric::FootprintDiameter()` = 56 cm x cell / 150), instanced thin bars lying flat on the board plane in actor space so they do not tilt with a fallen figure. The active, selected and target markers are larger rings of the same kind. The primitive look (`-ExpeditionPrimitives`) is unchanged: opaque base discs under figures and flat disc markers. The hold-for-full-grid key (Left or Right Alt) sets `FBoardHighlights::bFullGrid` through the controller; it never reaches the rules, session or checkpoint.

### Rigged characters and the animation seam (#147)

`UDiceRollTheme` holds `FighterRig`, `WizardRig` and `RaiderRig` (`FDiceRollCharacter`: a skeletal mesh on the one shared skeleton, the nine clips by role, a yaw offset). `AExpeditionBattleView::UnitRigged` maps them to the roster (party Fighter and Wizard, the enemy raider by the same rule as `UnitMesh`); every other unit, and any unit whose definition lacks the mesh or a clip, falls back to its static r001 mesh and then to primitives. `-ExpeditionPrimitives` still forces primitives and `-ExpeditionStaticFigures` (or `UseStaticFigures()`) draws the static set.

The seam is a value, not a graph. `Presentation/UnitPose.h` names the nine clips (`EUnitPose`) and holds the pure choices: move to Walk, attack to Melee or Ranged (more than one cell away), spell to Cast, damage that leaves the target standing to Hit, downing to Downed, death to Death, healing a downed unit to Recover, otherwise Idle; `Rest(Life)` is the pose a committed life implies (Death, Downed or Idle). `FExpeditionPlayback` sets `FUnitDisplay::Pose` from the committed result at the step that shows it and bumps `PoseSerial`; it never reads the pose back and rules never see it. `Sync`, `Reset` and `Finish` converge every display on `Rest(Life)` (`bPoseSnap`): a reset, resume, skip or instant playback therefore shows the end of the committed state with no animation, and a settled queue lets a one-shot clip play out before Idle.

The view animates with single-node animation (`PlayAnimation`, then `SetPosition`), not an Animation Blueprint: it keeps the clip and its time per figure and advances the time itself at playback speed, so a figure's pose is a function of the display state and the clock, and `UnitAnimation(UnitId)` can be read by tests. A snap shows Death and Downed at the last frame of their clip and Idle at a per-unit phase. A rigged figure stands on its cell at the metric's figure height with `UnitRigRoot` as its root; the clips supply the fall, so the primitive hop, breathing squash and tilt do not apply. Checkpoints and snapshots are the same with rigged, static or primitive figures.

## Native build catalog (#39)

`FBuildCatalog` exposes const definitions, atomic construction with independent adventurer ID/name, compact special-action membership, milestone damage and resource validation. The immutable profiles and bounded recovery caps are authoritative for expedition construction and detached restore. Non-Fighter `.base` IDs are interim current kits, not claims of implemented book subclasses. Standalone combat still accepts bounded custom fixtures without catalog identities; expedition restore requires catalog identities and the current catalog revision. The selected-party overloads of run/session NewRun accept exactly four ordered IDs 1–4 with bounded names and catalog build IDs, constructing on a detached candidate. Legacy Fighter shortcuts delegate to the same construction. `FBuildCatalog::All` enumerates only implemented kits; definitions use explicit records rather than positional class dispatch. Four Barbarian paths use generic Special1/Special2 commands resolved through catalog ability facts; old named commands remain compatible. Reflected RageUses/RageTurns/GuardTargetId/LastSurge fields are bounded and restored without ticking. Startup editing and presentation use the bounded class/kit controls delivered in slice 2 of #37. The slice 3 martial extensions and revision 3 ownership/duration contract are recorded in [the martial kit reference](runs/full-roster/05-martial-kits.md).
