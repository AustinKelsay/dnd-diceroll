# Architecture conventions

Use C++ for stable foundations, reusable logic, integration, and behavior that benefits from native debugging or performance. Blueprint children can configure C++ parents and implement presentation and appropriate event behavior. Choose the boundary for the feature; avoid a C++-only rule. Keep related code cohesive inside the existing runtime module until a real dependency or loading boundary justifies another Unreal module. [Epic: C++ and Blueprint](https://dev.epicgames.com/documentation/unreal-engine/coding-in-unreal-engine-blueprint-vs-cplusplus)

For persistent strong references to reflected UObject members, use `UPROPERTY()` with `TObjectPtr<T>`. An unreflected `TObjectPtr` alone does not protect lifetime. Use `TWeakObjectPtr` for non-owning references that may expire, and `TSoftObjectPtr` for asset references that should support deferred loading. Raw pointers remain appropriate for short-lived locals and parameters when lifetime is established; validate references at use boundaries. [Epic: object pointers](https://dev.epicgames.com/documentation/en-us/unreal-engine/object-pointers-in-unreal-engine)

Expose purposeful tuning and configuration properties with suitable edit permissions, categories, tooltips, units, and editor ranges. Prefer limited access such as `EditDefaultsOnly` or `BlueprintReadOnly` where appropriate. Enforce invariants in runtime code too: metadata clamps only guide the editor and are not runtime validation. [Epic: metadata specifiers](https://dev.epicgames.com/documentation/en-us/unreal-engine/metadata-specifiers-in-unreal-engine)

Choose delegate features separately. Native versus dynamic concerns reflection, Blueprint access, serialization, and overhead; single-cast versus multicast concerns listener count. Multiple listeners alone do not require a dynamic delegate. Specify subscription ownership and unbinding when adding listeners, and avoid a global event bus without concrete requirements. [Epic: delegates](https://dev.epicgames.com/documentation/en-us/unreal-engine/delegates-and-lambda-functions-in-unreal-engine)

The boilerplate supplies infrastructure and a sandbox fixture. Add controllers, UI, navigation, networking, materials, or gameplay frameworks when an approved slice needs them. Do not rename internal Unreal identifiers as part of routine feature work; module/package renames require a separate migration.

## Expedition persistence

`FCombatBattle::Restore` and `FExpeditionRun::Restore` validate detached values before installing them. Restore never calls Start/NewRun, generates offers, rolls initiative or spends RNG. Combat validation checks bounded stats, grid/occupancy, life/HP/deadline consistency, enum values, initiative/order/active actor and budgets. Run validation checks selected catalog profiles and recipe facts, phase/completion/history/offer relationships, one camp, artifact state and reward-derived equipment/consumable allowances. This is coherent bounded-state validation, not a replay proof or tamper-proof format.

`FExpeditionSave` encodes version 5 value-only JSON (versions 1–3 are rejected as unsupported) with required fields and exact types, then validates the complete document. Decode explicitly upgrades format 4 to 5 by adding Compact ruleset and default combatant/encounter fields before strict import; current-format documents still require every field. Unknown future versions are rejected, not rewritten. `FExpeditionSession` owns the live run for the player adapter. Every accepted party command, whole enemy turn, route, reward, recovery and new run is evaluated on a candidate. The candidate and any deduplicated ending record are written together before installation. A write failure rejects the candidate, including its random progression and deaths. Save is an explicit confirmation of this same checkpoint; Resume reads the latest committed file. There is no stale backup fallback. Presentation only submits session commands and observes const run queries.

The local file adapter writes a sibling `.pending` file. On Linux and macOS it replaces the destination with a same-directory rename. If that rename fails while the old file exists, the Linux build moves the old checkpoint aside to `.previous`, installs the new file, and restores the old one on failure. On Windows the same `.pending` file is installed with one `MoveFileExW(MOVEFILE_REPLACE_EXISTING | MOVEFILE_WRITE_THROUGH)` call (write-through is best-effort, not a durability guarantee), so the prior checkpoint is never absent; if a non-replacing fallback cannot restore the prior file, the error names the `.previous` path instead of claiming it was retained. A failed write/rename preserves the prior valid checkpoint and history. The adapter does not promise fsync/power-loss durability, cloud sync, multiple writers or arbitrary migration across save versions/platforms. A stale live session is rejected if its current value differs from the disk checkpoint. Startup does not write a run. Records contain identity, seed, outcome, victories and survivors/summary; they never enter party construction or power calculations.

Fresh runs use one GUID at construction. The seed remains the reproducible gameplay input; tests can supply an explicit run identity. Loading retains that identity. Default storage is `FPaths::ProjectSavedDir()/SaveGames/Expedition/current-v1.json`; native validation can select an isolated directory through `-ExpeditionSaveRoot=<directory>` or `EXPEDITION_SAVE_ROOT`. No reflected UObject or presentation selection/camera value enters a save.

A packaged Linux Development game resolves that default under `~/.config/Epic/DnDDiceRoll/Saved/`. (The earlier sandboxed Mac app used `~/Library/Containers/com.YourCompany.DnDDiceRoll/…`, where overrides outside its sandbox could be unreadable.) Native fixtures must use an owned directory the game can access. The editor's default remains the project's `Saved/` directory.

NewRun also enforces unfinished-run protection at the session boundary, including a saved run not yet resumed after startup. An explicit startup NewRun can recover an unreadable/incompatible file by moving it to a unique sibling `.unreadable-…` path; its bytes remain preserved, even if writing the replacement fails. The optional preserved-path result drives visible recovery feedback. Resume never accepts invalid data (the explicit format 4→5 upgrade is supported), and an active session never quarantines its checkpoint. This is recovery from an unreadable document, not an older-save fallback; it is separate from the explicit format 4→5 migration.

**Catalog revision (#184, #188).** `FExpeditionProgress::CatalogRevision` is the rules interpretation a run was created under, and a run keeps it for its whole lifetime. New runs use `FBuildCatalog::Revision` (9); `NewRun` also takes an older supported revision explicitly (tests and the balance harness's before-run). Restore accepts `FBuildCatalog::MinimumRevision` (7) to `Revision`; any other revision is refused with a message naming it and the supported range, and the file is preserved like any unreadable checkpoint. Generation and restore read enemy stats through one function, `EnemyStats(Ruleset, Revision, …)` in `Run/ExpeditionRun.cpp`, with explicit Compact and SRD cases. Compact runs at revision 8 get the tuned enemies. Compact runs at revision 7 (including format 4 saves) and every SRD run get the revision 7 enemies, for already-spawned and future encounters alike, so an existing checkpoint resumes and continues exactly as before. An unsupported ruleset or revision fails generation instead of guessing. Revision 9 Compact runs add encounter identity: stage recipes (0–2 approach, 3–5 pressure, 6 the front-to-back vault sanctum), saved enemy roles in `FCombatantState::Role` (`Raider`, `Archer`, `Skirmisher`, `Brute`, `Warden`) with their speeds and stats, and four-line previews. Revision 9 draws the generation random numbers in revision 8's order (the drawn 0–2 plus 3 for pressure; the finale draws and ignores it), so fights 1–2 keep their boards. `FExpeditionRun::EncounterLayout` is the pure query generation and restore share (board, obstacles, spawns, enemies for a route at a stage, ruleset and revision), and `FExpeditionRun::Encounter(Progress, Route)` returns the `FEncounterIdentity` presentation may read (stage, obstacle kind 0 stones/1 pillars/2 walls, layout name, front-to-back), derived from saved fields only; neither rolls.

`FExpeditionSession::Close()` (Return to menu, #132) only drops the live run from memory: it writes, moves or deletes nothing, so the checkpoint stays as last committed, Resume restores it and NewRun's unfinished-run protection still applies. `HasUnfinishedCheckpoint()` is the matching read-only query (a readable, unfinished checkpoint) that lets the start screen focus Resume.

## Expedition presentation

The rules settle each command instantly and return an `FCombatResult` with presentation facts: actor, target, the path walked, every damage or healing die in roll order, and who was newly downed or killed. Rules never read these back. `FCombatBattle::Forecast`, `PathTo`, `ActionReach` (reach and blocked-sight cells, independent of budgets and eligibility) and `Protection` (the reduction the next hit on a combatant loses to, and who supplies it; the same function resolution applies, #179) are const queries that share resolution tuning and consume no random numbers. The controller's `ShowsTargeting()` is the one gate for targeting feedback (reach markers, target chips, board highlights): a party member has the turn in a fight, no overlay is open and no playback is running. The HUD reads the controller's reach and targets for the frame instead of recomputing them.

`FExpeditionPlayback` (plain C++) replays committed results as timed steps and owns only display state: unit positions, displayed HP, floating text, projectiles, the dice tray (the roll card, placed in the left margin outside the camera's board area, #190) and turn banners. `Finish` completes every queued step silently and always converges on the committed snapshot. An accepted player command finishes earlier playback before its own plays; rejected input leaves playback alone. Resume, new runs and route changes rebuild and reset it; loot and camp sync the display after committing; Save changes no state. Animation therefore never delays, reorders or duplicates an outcome. Enemy turns start only when playback is idle.

`AExpeditionBattleView` maps the playback onto runtime primitives (themed scenery per route, character figures, markers, effects, lights, camera) and plays synthesized cues. `AExpeditionPlayerController` turns input into commands for the active adventurer. Pointer motion hands the board back from the keyboard cursor, and a click acts only on the cell the last frame previewed under the pointer (#171); tests drive this through `SimulatePointer`, since a transient world has no viewport. It also holds the contextual combat hints' state (`FCombatHints`, #158): presentation only, in memory, never in a checkpoint; each frame it observes the acting hero's `FActionFactsQuery` facts and the snapshot (rebuilt only when the combat state changes) and hands the HUD at most one callout to draw. `AExpeditionHUD` draws the Canvas interface in a 1280-wide design space and registers clickable buttons while drawing. `Project.Tools.CaptureFixtures` writes real checkpoints for each expedition phase under `Saved/CaptureFixtures/` for visual QA; launch with `-ExpeditionSaveRoot=<fixture folder>` and resume.

### Action dock text (#58)

`FActionFactsQuery` (`Combat/ActionFacts.h`) is the one source of an action's cost, spent resources, stance, target shape, availability and exact blockers; it reads only the public battle API and consumes no random numbers. `ExpeditionStyle` (`Presentation/ActionText.h`) turns facts into words: cost and resource names, the cost and usage tags, usage lines, blocker text and tooltip headline, each by an exhaustive switch walked by a test. `AExpeditionHUD::DrawActionBar` takes its button list from `FActionFactsQuery::BarFor` and draws tags and tooltips from those helpers only, drawing none while `ShowsTargeting()` is false. It publishes what it asked to draw (`ActionTagsRequested`, `ActionTooltipRequested`) for tests, and `DockTextComesFromFacts` fails if cost or usage wording is hard-coded in the dock code. The dock keeps its facts and text until the combat snapshot changes. `ForBuild` gives the same facts without a battle for the build picker. A rejected command is explained by the first blocker when the facts describe it. A tooltip shows for hover and, through `AExpeditionPlayerController::ModeTipActive`, for a mode chosen by key; both build the same request from the same facts. Descriptions (`DescribeAction`, `FAbilityFacts::Description`) are effect, target and range text only; they are not saved and the catalog revision does not depend on them.

### Board metric (#141)

`FBoardMetric` (`Presentation/BoardMetric.h`) is the one presentation metric of a battle board: cell size in cm (default 150, a true 5 ft cell), figure height (default 180 cm), and from the cell the board top and the pointer plane. `AExpeditionBattleView` owns it and reads it from `UDiceRollTheme::CellSize` and `FigureHeight`; the primitive fallback uses the same defaults. `CellPosition`, `BoardPosition`, `CursorCell`/`CellAtRay`, camera focus and distance, markers, the targeting overlay and chips, projectiles, effects and playback hop heights all go through it; no other file may hold a cell size. Positions are relative to the view actor.

The r001 art, the camera framing and the poses were authored for a 110 cm cell (`ReferenceCellCm`). Scenery (world, tiles, obstacles, decor, markers, projectiles, effects) lives under a root scaled by `Scale()` = cell / 110 and is written in those reference units, so today's art still fits the board. Unit rigs scale the same way (bases and rings grow with the cell) and their bodies are fitted to the figure height. Camera distances, the zoom clamp (900 to 6400) and capture pose distances stay in reference units; the camera multiplies them by `Scale()`. The whole-board fit is solved, not approximated: `ExpeditionCameraRig::FitDistance` projects the four board corners (at the board top) through the real camera pose and the HUD-safe rect (`ExpeditionLayout::BoardBounds`, shared with the HUD layout; the HUD feeds the viewport to the view each frame) and returns the nearest distance that contains them. The default zoom is the closer of that fit and the figure-sized distance (see the battle camera section). Unreal keeps the vertical FOV of a 16:9 view at any viewport (MaintainYFOV), so ultra-wide screens see more width. The home-yaw whole-board fit anchors the pitch ramp (`FramedDistance()`); orbiting from the default zoom re-derives the default for each new yaw (the whole-board fit differs per yaw: a long board needs more distance end-on than side-on) while a zoom the player chose is kept; `ExpeditionLayout::BoardBounds` also keeps the board clear of the tallest combat log (`ExpeditionLayout::LogRect`, shared with `DrawLog`); while the whole board is in view the active-unit lean may only use the slack inside the safe rect. Metrics never enter rules, generation, saves or checkpoints (ADR-0001).

### Battle camera and lighting (#143)

`Presentation/CameraRig.h` holds the camera math as pure functions (distances in reference units, so `FBoardMetric` scales them): field of view 40; pitch from zoom, 35 degrees at 1300, 45 at the board's framed distance and 60 at `FarStop(anchor)` (1.4 x the home-yaw framed distance, at least 3000, at most the zoom maximum), linear between and clamped; and a pan bound that keeps the visible ground within 1.5 cells of the board (below). The framed distance fits the board into the screen area the HUD leaves free (`FSafeRect`, a parameter until the HUD layout settles), and the same rectangle slides the view so the focus lands in the middle of that area. Pan comes from Shift+W/A/S/D and middle-drag (plain A stays attack mode) and returns to the active unit when the turn changes. The tabletop overview keeps its own fixed camera, field of view 50. What it draws is `Presentation/OverviewLayout.h`'s (#149): the r002 war table and a diorama per road (the forest for guarded roads, the cathedral for dangerous roads, the Vault for the finale), or the r001 set when the r002 one is incomplete or fails to load, chosen as a set by `UDiceRollTheme::LoadOverview()`; presentation only.

**Default framing and pan bound (#148 gate 2).** The default zoom targets figure size, not the whole board. `FigureDistance` finds, by bisection through the real projection, the distance at which a standing figure (`FBoardMetric::FigureCm`, 180 cm, feet on the board top) at the focus covers `FigureTargetPixels` (88) of `FigureTargetViewportHeight` (1080) viewport pixels, a fixed fraction of the viewport height (so about 59 px at 720). 88 is nominal: rendered figures read at about 0.8 of a 180 cm projection, so a default figure is about 72 px tall on screen at 1080, using the camera's field of view, the framing slide and the pitch the zoom ramp gives that distance. The default (`DefaultDistance`, `AExpeditionBattleView::FramedDistance(Yaw)`) is `min(whole-board fit for that yaw, figure distance)` clamped to the zoom range. The figure distance does not depend on the yaw, so orbiting a board that does not fit keeps one default; a board that fits at the closer distance keeps its whole-board fit (an 8 x 7 board, for instance; the generated 16 to 18 by 11 to 12 boards take the figure distance at 16:9). `FramedDistance()` without a yaw is still the home-yaw whole-board fit, the anchor of the pitch ramp, and `WholeBoardDistance(Yaw)` and `FarFramedDistance(Yaw)` (the far stop, never nearer than the fit for that yaw) keep "see everything" one zoom away: wheel-out and the capture `far` pose reach the whole-board fit, and the `FarStop` and the far pose are unchanged.

The focus follows what is framed. While the whole board is in view from the rendered pose, the focus leans 0.4 toward the active unit as far as the board stays in the safe rect, as before (`LimitLean`). Otherwise it centres on the active unit. The pan bound then clamps it (`ClampPan`): the ground the safe rect shows (`VisibleGround`, the four screen corners unprojected to the board top; translating the camera translates it rigidly) may reach at most `PanMarginCells` (1.5) past the board's outer tile edge on each side, in board axes at the current yaw. An axis on which the view is wider than the board plus those margins is locked with the view centred on the board (the point the allowed interval shrinks to, so zooming or orbiting across that threshold moves the view continuously), and while the whole board is in view nothing pans. The bound holds on every rendered frame, while the camera eases and while it shakes: a shake is clamped like a pan and kept level while the bound applies. Held keys re-pin to the bound instead of winding up past it; a turn change returns the view to the active unit; plain A is still attack mode. Unpanned, `KeepUnitInside` (`UnitFill` 0.9) then moves the focus toward the active unit only as far as the unit's tile and head are inside the safe rect, every frame (after the easing too), so at the default zoom on a board that does not fit the guarantee is the active unit and its footprint in the HUD-safe rect, and the whole-board guarantee holds wherever the whole board is what is framed (a fitting board, `far`, the whole-board fit). The unit hold takes precedence over the pan bound when the two disagree.

The key light casts cascaded shadows (4 cascades, 7000 reference cm). Of the flame lights, the two nearest the board centre (ties to the earlier light) cast shadows; all others, and every effect, stay unshadowed.

**Brazier ring and light budget (#148).** Braziers, their flames and their point lights stand around the board perimeter, not at fixed spots: `Presentation/BrazierRing.h` plans them as a pure function of board size and the encounter seed (the private `VigilKit::Unit` hash, no random stream, so it cannot reach rules, snapshots or checkpoints). Each edge has `max(2, length / 4)` braziers (one every four cells), at the middle of equal spans, 1.25 cells outside the playable edge (cell centres are at integers, so the edge is at -0.5 and `Width - 0.5`) and moved up to 0.25 cell along the edge by the seed. The count is `2 x (EdgeCount(Width) + EdgeCount(Height))`: 12 on 16 x 11, 14 on 18 x 12, and the same on every world, the r001 worlds, the Root kit and the Vigil kit, because it follows the board and not the kit. Standing 1.25 cells out puts a brazier past the overlay's gutter cell, past the occluder's half-cell board margin and past the half-cell margin of the camera sight volume the r002 worlds keep clear, and it cannot meet a blocked cell, an obstacle or an arch, which are all on the board. The kit's scatter keeps one cell from every brazier (`VigilKit::PlanDressing`'s `Avoid` parameter: other cells take the place of the ones it rules out, so the count and the default plan are unchanged). Banners and cages keep their places. Braziers and flames are instanced props placed with `PlaceProp`, so a brazier costs two instances and a light, never a component, and flames still flicker through instance transforms (`AddSway`).

The braziers share the light the seven of #143 gave a board: each light is `280 / count` candela (40 cd with seven, 23.3 with 12, 20 with 14), radius 900 reference cm unchanged, so the overall level matches before. Flicker still scales each light's own strength. Gate 1's cap of two shadowed local lights is kept by `SelectShadowLights` (`BrazierRing::MaxShadowed`): the two braziers nearest the board centre cast shadows and all the others are unshadowed, so a 16 x 11 board has 12 brazier lights and 14 on 18 x 12, two of them shadowed. Light attenuation radii are authored in reference cm and scaled by the metric in `MakeLight`. No Lumen, no virtual shadow maps.

### Contextual grid and footprint rings (#142)

Themed battle boards place no per-cell tile meshes: the world's flat ground is the playing surface (at board top), and `Presentation/BoardOverlay.h` draws the grid on it only while it carries meaning. `BoardOverlay::FMask` is a per-cell state mask (Move, Reach, Obstructed, Path, Hover, Victim bits) built each frame from `FBoardHighlights`, which the controller fills from the same rules queries #50 uses (`LegalMoves`, `ActionReach`, `PathTo`, `LegalTargets`, `Forecast`). `BoardOverlay::BuildBars` turns the mask into thin bars in cell units (reach contour runs with exact cardinal corners, corner ticks at lattice vertices inside reach, blocked-sight crosses, the path ribbon with a cost tick per step and a destination bracket, hover brackets, victim frames and, while Alt is held, the whole-board lines). The view draws one `UInstancedStaticMeshComponent` per style on the board plane through `FBoardMetric`; bars are rebuilt only when the mask, path, origin or key changes, and an unchanged frame neither builds a mask nor allocates (inputs are compared against reused scratch storage). This was chosen over a mask texture plus a distance-field floor material because it needs no texture, no per-frame texture upload and no custom shader: the only asset is the small translucent `M_BoardOverlay` ("Color" and "Opacity"), created by `Content/Python/create_board_overlay_material.py`. Without it the bars draw as dimmed opaque lines. The mask is also kept on primitive boards (tests read it), but only themed boards draw it; primitive boards keep tinted cube tiles and the HUD dots. The HUD still counts reach markers per cell and labels path length, AREA victims and chips, so #50's semantics are unchanged.

Figures stay readable behind tall scenery (pillars, arches) with a silhouette, not by removing or fading the obstacle: blocked footprints stay solid. `AExpeditionBattleView::SetFigureSilhouette` turns custom depth on for every figure part (the footprint ring is excluded) with stencil 1 for the party and 2 for enemies, from `UpdateRigs`; dead figures drop it, downed ones keep it. `AttachSilhouette` adds the optional post-process material `M_FigureSilhouette` (After Tonemapping; it mixes the side colour in where `CustomDepth` is farther than `SceneDepth` by more than a small tolerance, i.e. the figure is hidden) to the view's `Grade` blendables when the asset exists, so primitive boards and tests without it work. This needs `r.CustomDepth=3` (`[/Script/Engine.RendererSettings]`, `Config/DefaultEngine.ini`). The silhouette is on for primitive figures as well (the rig code and `AttachSilhouette` do not depend on the theme). `M_BoardOverlay` draws with the depth test off so overlay bars show through the same architecture. Side reads without colour (party solid, enemy hatched). Assets and graph: [assets.md](assets.md#dark-fantasy-theme-issue-38).

In the themed look only, figures stand on hollow footprint rings (`FBoardMetric::FootprintDiameter()` = 56 cm x cell / 150), instanced thin bars lying flat on the board plane in actor space so they do not tilt with a fallen figure. The active, selected and target markers are larger rings of the same kind. The primitive look (`-ExpeditionPrimitives`) is unchanged: opaque base discs under figures and flat disc markers. The hold-for-full-grid key (Left or Right Alt) sets `FBoardHighlights::bFullGrid` through the controller; it never reaches the rules, session or checkpoint.

### Drowned Vigil world kit r002 (#145)

The r002 kit (world, near-architecture occluder, three variants per obstacle recipe, 2-cell arch, scatter, mist cards, light shafts) is authored at the true 150 cm cell, unlike r001, so `AExpeditionBattleView` places it at `1 / Scale()` under the scaled scenery root. `UDiceRollTheme::bMetricKit` switches it on, and only the import script sets it, when the world and the three variant-A props are all r002 (they replace r001 packages together or not at all). Without it the board draws the r001 entries exactly as before, and `-ExpeditionPrimitives` never loads the theme.

`Presentation/VigilKit.h` holds the placement rules as pure functions of board size, blocked cells and the encounter seed, using a private hash (`VigilKit::Hash`) and no random stream, so the theme choice cannot reach rules, snapshots or checkpoints: obstacle variant per cell (`VariantIndex`), arches over adjacent blocked pairs of pillar and wall recipes only (`ArchesFor`, `ArchPairs`, scan-order independent; adjacent stones get none), and scatter, mist and light shafts (`PlanDressing`), which stand at least two cells outside the board (mist and shafts three), so nothing lands on a playable cell or on the overlay contour. `Presentation/OccluderFade.h` is the dither-fade rule of the occluder mesh. Its material (`M_DiceRollOccluder`, masked, created once by the import script) evaluates the same formulas per pixel, and the lower opacity wins. The board test (`OccluderFade::Board`) casts the ray from the camera through the pixel to the board-top plane and dithers the pixel toward 15 % when the hit lies in the board rectangle grown by half a cell and the pixel is nearer the camera than the hit, easing back to opaque over half a cell outside it; `UpdateOccluder()` gives it `BoardRect`, `BoardZ` and `BoardRamp` only when they change (`OccluderBoard()`). The sight-line test (`SightEye`, `SightFocus`, `SightUnit`, `FadeRadius`, `FadeMin`, pushed every frame) is kept for a figure at the board's far edge, whose covering pixels land past the rectangle. Everything else stays opaque, so the mesh is never hidden. The occluder material also carries the master's `CameraFade` clip (#143: scenery nearer the camera than 0.5 x its height is cut), multiplied with the dither, so geometry around the camera never swallows it and what blocks the view dithers; the world and props keep only the master's clip. `OccluderOpacityAt` (sight lines), `OccluderBoardOpacityAt`, `PlacedDressing`, `ObstacleVariants` and `ObstacleSpots` expose what was built for tests.

### Root of the World world kit r002 (#149)

The Root kit is the forest equivalent of the Vigil kit and goes through the same placement. `UDiceRollTheme` gains `bRootMetricKit` and the `Root*` entries (`RootOccluders`, `RootPillarVariants`, `RootWallVariants`, `RootStonesVariants`, `RootArchTwoCell`, `RootScatter`, `RootMistCards`, `RootLightShafts`); the world keeps `RootWorld`, whose package the r002 export replaces. `UDiceRollTheme::KitFor(EDiceRollKit)` (it was `KitFor(bForest)` until the Vault) returns an `FDiceRollWorldKit`, a plain struct of the metric flag and views of the properties for the world being built, so `BuildThemedScenery`, `BuildKitObstacles` and `BuildKitDressing` have one path for both worlds and do not name Vigil or Root properties. Meadow boards read the Root kit, Ruins boards the Vigil kit and the finale the Vault kit (below), which falls back to the Vigil kit. `bRootMetricKit` is set by the import script only when `SM_World_Root` carries the root r002 tag; with it off a Root board draws the r001 world scaled by the metric, as before. Obstacles keep their old chain: the world kit's variants, else (a forest board with the Vigil kit on and no Root variants) the Vigil variants without arches, else the shared r001 packages.

`VigilKit.h` keeps its name and rules for both worlds (a seeded outcome places the same cells whichever world draws them); the arch rule is shared, so the Root's pillar and wall recipes take the 2-cell arch and its boulder stones do not. A kit part honours the `Color` tint stored on its own material instance (`KitTint`). Instanced, it draws with that material instance, so the tint applies as is; loose, the tint is multiplied into the part colour (`InstanceTint`), because the part's dynamic material would otherwise overwrite it. So the lead can lower the Root paving by editing the instance (`INSTANCE_TINTS` in the import plan) rather than re-exporting. `UsesRootKit()`, `WorldMeshScale()` (1 for a kit world, the metric scale for r001) and `UseTheme()` (a swapped theme, for fallback tests and captures) expose the choice; `Tests/RootKitTest.cpp` covers it, and the figure-height and silhouette checks run on a Root r002 board there as well as on the shipped theme in `BoardMetricTest`.

### Vault world kit r002 (#149)

The finale (encounter 5, `EBoardTheme::Vault`) has its own world. `EDiceRollKit { Vigil, Root, Vault }` names the three kits and `AExpeditionBattleView::KitKindFor(EBoardTheme)` maps a board theme to one: Meadow to the Root, Ruins to the Vigil, the finale to the Vault. `UDiceRollTheme` gains `VaultWorld`, `bVaultMetricKit` and the `Vault*` entries (`VaultOccluders`, `VaultPillarVariants`, `VaultWallVariants`, `VaultStonesVariants`, `VaultArchTwoCell`, `VaultScatter`, `VaultMistCards`, `VaultLightShafts`); the import script sets the flag only when `SM_World_Vault` carries the `vault-kit-r002` tag. `KitFor(Vault)` returns the Vault kit only when `VaultKitComplete()` (the flag and every entry set, and every entry's package present: world, occluders, 3 + 3 + 3 variants, arch, 8 scatter, 3 mist cards, 2 shafts; a reference to a deleted package counts as missing); otherwise it returns the Vigil kit, so a theme with any Vault entry missing or dangling draws the finale exactly as before. The fallback is atomic: `BuildThemedScenery` loads every Vault piece (`VaultPiecesLoad`) before it places anything, and one that does not load (a package that exists but fails to load) sends the whole finale to the Vigil kit, never a half kit. `FDiceRollWorldKit` gained `Kind` and `World`, so one placement path serves all three kits. The Vault has no iron cages (it has its own chains).

**The Waystone light.** The finale has always carried a Waystone: a floating shard over a pedestal in the far-right corner and a cyan point light (`WaystoneSlots`, `WaystoneLight`, intensity 200, or 320 once the artifact is recovered, with its flicker). With the Vault kit active the world's own Waystone in the apse leads the composition, so the legacy pedestal is not drawn (its slot is hidden, so the shard animation keeps working) and the shard and the one light stand at the apse, 13.55 m behind the board centre on the centre line (`VaultApseOffsetCm`), the shard 1.5 m in front of the monolith; the light keeps its intensity and artifact behaviour times `VaultWaystoneGain`, and the shard's emissive is scaled by `VaultShardGlow`. The Vigil fallback keeps the legacy pedestal. `WaystoneLightCount()`, `WaystoneLightLocation()` and `WaystoneDrawsPedestal()` expose it; `VaultKitPlacementIsDeterministic` asserts one light, at the apse, and no pedestal.

Obstacle variants and dressing use `VigilKit::KitSeed(Seed, Width, Height, Kind)`, the finale's own decoration seed: a private hash of the board size, the encounter seed and the kit kind (the Vigil and the Root pass the encounter seed through unchanged, so their shipped boards do not move). It never reads or advances rules state or any random stream, so the finale's checkpoint bytes and snapshots are the same under any presentation (`VaultThemeChoiceLeavesStateUnchanged`). The braziers keep the encounter seed. Dressing stays two to five cells outside the board (never on a playable cell, any size 16 to 18 by 11 to 12: `VaultDecorationNeverStandsOnAPlayableCell`).

The Vault world is mirrored in Y on export: the glTF to Unreal import mirrors Y, so the Waystone and the back wall (designed on +Y) stand on the far side of the home camera, with the front open. The occluder mesh carries the walls, which dither when they come between camera and board, as the Vigil's and the Root's do.

**Vault grade (#149).** The finale keeps the Vigil's biome grade structure (`GradeFor`, `ThemedPaletteFor`) with a calmer palette: a pale moonlight sun (0.62, 0.7, 0.95) at 1.5, fog (0.05, 0.065, 0.12) at 0.04, saturation 0.8 in battle, an exposure band centred on 0.10 (was 0.09) and the vignette 0.25. Gate 2 found the far view dim and flat, so the Vault has a **far-zoom grade** (`UpdateFarGrade`, called every frame from `UpdateCamera`): from the default zoom out to the far stop (`FarFramedDistance`) a smoothstep lifts the exposure by up to 0.62 (about 0.7 stop) by dividing the fixed luminance band by the lift (UE's exposure scale is the inverse of the clamped luminance, so multiplying the limits, as the first version did, darkened the far view), cuts the vignette by 60 % and raises contrast from 1.12 to 1.2, rewritten only when the amount moves by 1 %. **Measured before and after, Vault only, the same far pose** (`board-vault`, yaw -90, 1920 x 1080, the board floor region and a dark surround region, Rec. 709 luma of 8-bit values): with no far grade the floor reads mean 35.0 (spread 25.5) against a surround of 18.4; the first version (limits multiplied, the wrong direction) read **20.2** against 8.6, a darker far view than none at all; the fixed grade reads **40.3** (spread 25.9) against 21.9, 15 % brighter than no grade and 2.0 times the first version. At the default zoom the floor reads 30.9. The Vigil and the Root keep their grade: on the gallery's `board-vigil-walls` and `board-root-r002` (default and far, same crop) the far view is already no darker than the default, so there is no measured win to take there.

### Rigged characters and the animation seam (#147)

`UDiceRollTheme` holds the rigs as data (#150): `ClassRigs` and `FoeRigs`, `TMap<FName, FDiceRollCharacter>` keyed by the party class's enum name (`Fighter`, `Rogue`, `Cleric`, `Wizard`, `Barbarian`, `Monk`, `Paladin`, `Ranger`, `Sorcerer`, `Warlock`, `Druid`, `Bard`, `Artificer`; `UDiceRollTheme::ClassKey`) or the foe archetype (`Raider`); an entry is a skeletal mesh on the one shared skeleton, the ten clips by role and a yaw offset. `RigForClass` and `RigForFoe` resolve them; a later cast batch gives a class a rig by adding its entry (the import script's `RIG` table), with no code change. The pilot fields `FighterRig`, `WizardRig` and `RaiderRig` remain only so a theme saved before #150 still resolves; the maps win when both are set. `AExpeditionBattleView::UnitRigged` maps a unit to its definition (a party hero by `AdventurerRole`, the enemy raider by the same rule as `UnitMesh`); every other unit, a class with no entry, and any unit whose definition lacks the mesh or a clip fall back to its static r001 mesh and then to primitives. `-ExpeditionPrimitives` still forces primitives and `-ExpeditionStaticFigures` (or `UseStaticFigures()`) draws the static set.

**Subclass palettes and party accents (#150 batch 4).** `Presentation/ExpeditionPalette.h` (`namespace ExpeditionPalette`) recolours a rigged party figure without a new mesh, atlas or material instance asset: `ForUnit` maps a hero's build id (`FCombatantState::BuildId`, keyed by `ClassId`) to an `FPalette` of four slots (A primary garment, B secondary garment, C trim, G glow) from the generated table `ExpeditionPaletteTable.inl` (authored in `Art/rig-pilot/cast/palettes/palettes.json`, compiled by `Art/rig-pilot/cast/scripts/palettes.py`); an unknown build falls back to its class default (the class's own colours, except the fighter's corrected steel) and an unknown class gets no palette. `AccentSlots` gives each party member whose class appears more than once in the party its position among the party in encounter order, and `SetAccent` turns on slot X, a small per-class accent region (never a base tile), with a hue keyed to that position (red-orange, blue, green, amber, wrapping); `-ExpeditionNoAccents` drops only the accent. `AExpeditionBattleView::BuildSkeletalFigure` writes the result to the figure's own dynamic material instance (`PalMask<slot>`, a bit mask over the 13 atlas tiles, and `Pal<slot>`, the target colour with the class's reference luminance in alpha); the master material's palette block replaces a masked pixel by `target x min(luminance / reference, 1.7)` so a tile keeps its folds and highlights. Both mappings are pure functions of the committed encounter that take it by const reference: neither reads or writes a snapshot, a checkpoint or a random draw (ADR-0001), so Resume, `Finish()` and skip show the same colours, and `-ExpeditionNoPalettes` (the gallery's `--no-palettes`) turns them off for before/after captures. `AExpeditionBattleView::UnitPalette` reads a figure's palette back from its material (tests).

A rigged figure draws through its `USkeletalMeshComponent` (`Rig.Skin`), not `Rig.Parts`: the view creates one dynamic material per skin slot (kept in `Rig.Parts` with no mesh, so hit flash, glow and rim tint reach it through `Color`) and `SetFigureSilhouette` sets the skin's custom depth and stencil by side. Capture runs can hold a rigged hero in any clip at any time (`PreviewPose`, the `pose` capture mode); it changes no state.

The seam is a value, not a graph. `Presentation/UnitPose.h` names the ten clips (`EUnitPose`; Brace is the tenth, #150) and holds the pure choices: move to Walk, attack to Melee or Ranged (more than one cell away), a spell to Cast, a non-spell self or ally effect (Rage, Second Wind, a non-spell ward or touch) to Brace, damage that leaves the target standing to Hit, downing to Downed, death to Death, healing a downed unit to Recover, otherwise Idle. A catalog ability's clip is `ForAbility`, from its `bSpell`, effect and target: a spell casts (swaps and mitigation have no clip), a non-spell attack (Strike, WeaponAttack, Area, Push, Surge, Missile) swings or shoots, and a non-spell Rage, Protect or Healing braces; the fixed commands are `ForCommand` (Second Wind braces, Cure Wounds and Magic Missile cast, a potion, a rescue and End Turn have no clip); `Rest(Life)` is the pose a committed life implies (Death, Downed or Idle). `FExpeditionPlayback` sets `FUnitDisplay::Pose` from the committed result at the step that shows it and bumps `PoseSerial`; it never reads the pose back and rules never see it. `Sync`, `Reset` and `Finish` converge every display on `Rest(Life)` (`bPoseSnap`): a reset, resume, skip or instant playback therefore shows the end of the committed state with no animation, and a settled queue lets a one-shot clip play out before Idle.

The view animates with single-node animation (`PlayAnimation`, then `SetPosition`), not an Animation Blueprint: it keeps the clip and its time per figure and advances the time itself at playback speed, so a figure's pose is a function of the display state and the clock, and `UnitAnimation(UnitId)` can be read by tests. A snap shows Death and Downed at the last frame of their clip and Idle at a per-unit phase. A rigged figure stands on its cell at the metric's figure height with `UnitRigRoot` as its root; the clips supply the fall, so the primitive hop, breathing squash and tilt do not apply. Checkpoints and snapshots are the same with rigged, static or primitive figures.

### Instanced presentation parts (#144)

A themed board is drawn from a few dozen components, not a few hundred. `AExpeditionBattleView` keeps `Groups`: one `UInstancedStaticMeshComponent` per (mesh, material, shadow) triple, created on first use under the scenery root by `GroupFor` and destroyed with the rest of `Spawned` on rebuild (instance buffers go with the component, so a rebuild neither leaks nor reuses components). Placed through `PlaceProp`/`PlaceOccluder`, a prop is an `FExpeditionInstance` (group and index) plus its scenery-local transform, never a component, so `PropActorPosition` (obstacle spots, dressing positions) does not need one.

Instanced groups use GPU LOD selection, scaled per group by the mesh's sphere radius over its box extent (`MatchLooseLod`), so each instance picks the same LOD a loose component would at that distance. What is instanced (themed look only): the underlay, world, near-architecture occluder, kit obstacle variants and arches, r001 obstacles, scatter, mist cards, light shafts, braziers, flames, cages and banners; the pooled effects (4 shots and 16 sparks on one sphere group with the camp stones, the camp logs, the camp flames, the Waystone's two parts); the footprint rings and the markers, which are slots in one **bar bank** (`AddRingSlot`/`SetRing`: 24 bars per ring in one component, in actor space, hidden by a zero scale), and the contextual grid of #142, whose bars for all nine styles follow the rings in the same component (`OverlayBase`, `SetOverlayBars`: the bank only grows, a smaller grid collapses the leftover bars, and an unchanged frame still builds nothing). What stays an individual component, as before: anything that moves or animates per figure (the rig roots and bodies, rigged `USkeletalMeshComponent`s, static figure parts, which tilt when a figure falls and carry the per-figure custom depth and stencil of #145), the camera, lights, fog and post-process, and the tabletop overview's few parts. The primitive look (`-ExpeditionPrimitives`) never instances: `BasicShapeMaterial` cannot read custom data and its colours are random per part, so one material instance per colour group would be one per part anyway.

Tint and colour are per-instance custom data, so one material serves a whole group. Flicker and sway are not material values: a flame's flicker is a scale pulse on its geometry (plus its light's intensity), and banners and cages sway. So they stay transform-driven, as before #144, through per-instance transform updates that mark their group dirty once per frame (`FlushGroups`). That keeps the look identical, at about +0.05 ms of game thread on a Vigil board. Theme-material groups (`M_DiceRollTheme` instances, `M_DiceRollOccluder`, `M_DiceRollCard`) use the mesh's own material and one float, the brightness tint; the master multiplies `Color` by `PerInstanceCustomData[0]` (default 1, so skeletal figures and ordinary components are unchanged; graph revision `dice-theme-5`). Engine shapes in the themed look (sparks, shots, camp, Waystone, underlay) use `M_DiceRollEffect` and three floats, the colour, with the same lit base colour as `BasicShapeMaterial`; the bank uses `M_BoardOverlay` (revision `board-overlay-3`: emissive multiplied by `PerInstanceCustomData3Vector[0..2]`, opacity by `PerInstanceCustomData[3]`, defaults 1) with a neutral material instance, so each ring's and each grid style's colour and opacity are the same values the per-style material instances carried (bar thickness and lift are unchanged transforms). Groups tell the render thread once per frame (`FlushGroups` marks changed groups with `MarkRenderInstancesDirty`); sway props (flames, cages, banners) update their instance transform, and pooled effects (`SetSlot`) change only what differs and hide by collapsing to a point. Both effect materials are optional: without `M_DiceRollEffect` the pooled effects stay loose parts (and plain props use one `BasicShapeMaterial` instance per colour), without `M_BoardOverlay` the rings and the grid stay loose bar sets (one per style, dimmed opaque lines for the grid).

Test-only seams, no gameplay meaning: `SetLooseParts(true)` draws every part loose again (what the board drew before), `PresentationComponentCount` counts every primitive (drawing) component the board built, the grid, the rings and the figures included; lights and non-drawing scene roots are not primitives and are reported separately (the test logs the view's owned components), `InstancedGroupCount`, `LogicalPartCount` and `LogicalPropCount` count what was placed (the same loose or instanced), and `UsesInstancedParts`, `UsesInstancedEffects` and `UsesRingBank` say which path ran. `InstancedPartsTest.cpp` asserts fewer than 40 drawing components in total per themed rebuild (the #144 budget as defined on the issue), identical logical parts and props against the loose build, and no leak across rebuilds. Presentation only (ADR-0001): nothing here touches rules, sessions, saves or random streams.

## Native build catalog (#39)

`FBuildCatalog` exposes const definitions, atomic construction with independent adventurer ID/name, compact special-action membership, milestone damage and resource validation. The immutable profiles and bounded recovery caps are authoritative for expedition construction and detached restore. Non-Fighter `.base` IDs are interim current kits, not claims of implemented book subclasses. Standalone combat still accepts bounded custom fixtures without catalog identities; expedition restore requires catalog identities and a supported catalog revision (see "Catalog revision (#184)" above). The selected-party overloads of run/session NewRun accept exactly four ordered IDs 1–4 with bounded names and catalog build IDs, constructing on a detached candidate. Legacy Fighter shortcuts delegate to the same construction. `FBuildCatalog::All` enumerates only implemented kits; definitions use explicit records rather than positional class dispatch. Four Barbarian paths use generic Special1/Special2 commands resolved through catalog ability facts; old named commands remain compatible. Reflected RageUses/RageTurns/GuardTargetId/LastSurge fields are bounded and restored without ticking. Startup editing and presentation use the bounded class/kit controls delivered in slice 2 of #37. The slice 3 martial extensions and revision 3 ownership/duration contract are recorded in [the martial kit reference](runs/full-roster/05-martial-kits.md).
