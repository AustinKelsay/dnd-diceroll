# Development environment

## Baseline and upgrades

`tools/versions.json` pins UE 5.8.4 (CL 58902052) and records the validated host, **PlebDev Ultra**: Linux x86_64 (Omarchy), the engine's bundled Clang, an NVIDIA GPU with Vulkan, and Python 3.11+. The engine is installed at `~/Applications/UnrealEngine-5.8.4`; `UE_ROOT` selects another installation. Ultra is the only host whose Unreal results count for merges. The helper keeps its old Mac paths, but Mac is no longer validated; Windows is tracked in #51. Latest stable at setup becomes a reproducible baseline. Check Epic's release notes before upgrading, then repeat build, bootstrap, automation, identity/discovery, PIE, capture, and packaged startup checks before changing the pin.

Unreal MCP is experimental and bundled with the engine. `ModelContextProtocol`, `AllToolsets`, Python scripting, and Editor Scripting Utilities are editor-only. No separate community MCP bridge or Python service is required. `tools/project.json` explicitly selects the GitHub repository the contribution checks expect, the module, editor/game targets, content root, and automation prefix. The helper discovers one root `.uproject` (or requires `--project` when ambiguous) and reads `EditorStartupMap` from config. Unreal module/package identifiers use `DnDDiceRoll`.

Add `--cores 2` before the command on the shared machine (for example `python3 tools/dev.py --cores 2 build`). It caps compile actions, and engine cores for tests, bootstrap, the skill check, the editor, the cook, the packaged game and `perf` runs. Other commands refuse it. `build` fails on any compiler or build-tool warning. It only sees warnings from files it recompiles, so the merge gate builds each PR in a fresh checkout where every file compiles.

Run offline helper tests with `python3 -m unittest discover -s tools/tests -v`. Unreal-free geometry checks live in `tools/tests/native/`; see its [README](../tools/tests/native/README.md) for the compile recipe. `build`, `bootstrap`, `test`, and `package` refuse when this project is open, including when MCP is unavailable. Structural C++ changes use `status` → `close` → `build` → `editor`. Live Coding exists only for Win64 x64 in the installed engine; do not use it on Linux.

On Linux, `test` runs `UnrealEditor-Cmd` with `-RenderOffscreen` and `-ExecCmds="Automation RunTests <prefix>;SoftQuit"`. Do not add `-nullrhi`: it skips SDL setup and Slate then warns "Querying IsUsingWayland before SDL is initialized". Do not add `-TestExit`: on Unix it force-exits with code 1 even when tests pass. The helper also fails a build, test, bootstrap, skill check, or package run that changes any tracked file under `Config/`, even when the engine run itself failed; it reports the change and does not revert it.

The launcher refuses missing/stale build evidence and an occupied MCP port. A successful build records fingerprints of source, the project descriptor, module manifest, compiled binary, target, and pinned engine. Launch verifies that receipt rather than relying on timestamps; source deletions and no-action builds are handled correctly. It waits for readiness by default; `editor --no-wait` explicitly skips readiness. After an editor closes, Linux can hold the MCP port for about a minute (TIME_WAIT), and Unreal's listener cannot bind while it does. `editor` waits for the port to be free, and if Unreal still fails to bind it stops and tells you; close that editor from its window. MCP auto-start is disabled so headless automation cannot claim the editor endpoint. Only the controlled launcher passes `-ModelContextProtocolStartServer`.

## Identity, ownership, and closing

One agent owns the running editor. The helper serializes all its operations with a nonblocking local lock; other clients and a human editor user must still coordinate. Calls execute sequentially. Verify identity before mutation: the endpoint listener PID must be this project's process under the pinned editor executable, and the project toolset must independently report that PID, the canonical `.uproject` path, and the exact engine build. Matching map names or copied ProjectIDs is insufficient. An editor started outside the helper can be associated using the exact open project log, but still requires runtime confirmation. Saved launch metadata is advisory and never substitutes for live evidence.

`Content/Python/init_unreal.py` registers the small `unreal_starter.status.StarterWorkspaceTools` toolset. It reports both dirty content and dirty map packages, including unsaved packages. It creates no assets. It is pinned to the experimental UE registry API and registration safely does nothing when the registry is unavailable in a commandlet.

The same startup script imports the project authoring skill. [Unreal agent setup](agents/unreal-tools.md) covers optional Epic skills, compatibility rules, skill verification, and direct-connection recovery after editor restarts.

`close` refuses when PIE is active, packages are dirty, or identity cannot be proved. One small gap remains: a package could become dirty after the last check and before the quit request. On Linux no save dialog would catch it, so do not edit in the editor while `close` runs. Save intentionally in Unreal, check individual save outcomes, and re-run status. The helper neither silently saves everything nor discards changes.

On Linux, after those checks pass twice, `close` sends **one** SIGTERM to the verified editor PID and waits up to 120 seconds. Unreal treats the first SIGTERM as a normal exit request (exit code 143); a second signal forces exit, so the helper never repeats it and never uses SIGKILL. This path shows no save dialog, which is why the dirty and PIE checks are required. If the editor does not exit, the helper stops and reports it; check the editor yourself rather than signalling again. `close --request-quit` is refused on Linux. Never close an editor by name when several are running.

## Shared machine

Several agents use Ultra at once, and only one Unreal job may run at a time. A machine-wide lock file enforces that, so no one has to hand out turns. Ultra's host convention is `/home/plebdev/.t3/ultra-unreal.lock`; every checkout on Ultra must use this same lock.

1. Acquire the machine lock for each standalone native job: each `tools/dev.py` `build`, `test`, `bootstrap`, `verify-skills`, `gallery`, `perf` and `package` run, and each `UnrealEditor-Cmd` commandlet. Within an already locked editor session (item 3), run `smoke` and `capture` directly and sequentially without acquiring the machine lock again. Before a build, test, bootstrap, skill check, package or gallery run, close your editor, verify it exited, and release the session lock. Use `--cores 2` on the helper commands that accept it; omit it for `smoke` and `capture`, which refuse it. Direct commandlets use `-corelimit=2`. On Ultra, replace `relaunch` with `close` inside the existing session, verify exit, release the session lock, run a separately locked `build`, then acquire a new session lock before `editor`. For example:

   ```sh
   flock -w 7200 /home/plebdev/.t3/ultra-unreal.lock python3 tools/dev.py --cores 2 build
   flock -w 7200 /home/plebdev/.t3/ultra-unreal.lock python3 tools/dev.py --cores 2 test --filter Project.Expedition.
   ```

   The lock is held for that one job and released when it exits, so jobs from different checkouts interleave one at a time. `-w 7200` waits up to two hours for the lock; if it times out, report it rather than running without the lock.
2. For standalone jobs, keep each locked job short (about ten minutes or less where practical) so other agents are not starved; split long soaks or galleries into several locked runs.
3. Hold the lock for the whole time any Unreal process of yours is running, including a packaged game you are playing on screen and an interactive editor. Ultra has about 15 GB of memory, and two Unreal processes running at once have crashed a locked job's renderer under memory pressure. Keep such sessions to about 30 minutes, then close the game or editor and release the lock before re-acquiring it, so other agents' jobs can run. In a persistent Bash shell in your checkout, run `exec 9>/home/plebdev/.t3/ultra-unreal.lock`, then `flock -w 7200 9`. Proceed only if acquisition succeeds. Keep that shell alive throughout the session; run `editor` (or launch the packaged game) and subsequent helper commands there without additional machine-lock wrappers. Stop PIE, save intentionally, run `close` (or close the game normally), and verify your Unreal processes have exited before running `flock -u 9; exec 9>&-`. If closing fails, retain the lock and resolve it normally; never unlock merely because 30 minutes elapsed. A launcher script run under `flock` that starts the packaged game and waits for it to exit also works for a game session. Only one editor may own this project's MCP port (18765) at a time, so before `editor`, check for running `UnrealEditor` processes and a listener on that port, and close any editor you started with `close` and check that it exited.
4. Run jobs from your own checkout.

Never stop, signal, or force-quit another agent's process or editor, and never touch another checkout.

In editor builds capture mode also finishes all shader and asset compilation and flushes rendering on its first frame and on both sides of the frame-10 resume, as a start-up mitigation for the offscreen crash in #174 (a material's shader map replaced while a frame still draws with it). It is not a guarantee: later frames or a return to the start screen can queue more compilation, and the `Settling` stage waits only after frames have rendered, so a small residual window remains. Images captured before and after this change differ slightly on some fixtures (about 0.75 of 255 mean on `board-vigil-walls`, a uniform shift), so compare like with like. Capture mode only resumes and looks. It never submits a combat command (enemy turns are held) and never writes the checkpoint, and with `-ExpeditionCapture` absent the game is unchanged. The fixed time step and a fixed frame count after each pose make flame and idle motion repeat, and exposure adapts quickly (speed 20) so a shot does not depend on the one before it. Determinism limits: camera transforms repeat exactly; pixels repeat to within a mean absolute difference of about 0.03 of 255 on the same machine, GPU and driver (compare images with a tolerance, not byte equality). Results from another GPU or driver, or `-ForceRes` windows larger than the host desktop, are not promised to match. The enemy-turn view comes from the `default-seed-enemy-turn` fixture: fixture preparation (an automation test) ends the party's turns, and capture mode resumes with that enemy's turn held. Capture runs bind no keys or mouse buttons, so a focused capture window cannot act.

## Performance gate (#148)

`python3 tools/dev.py perf` measures one fixed fight on a **packaged Linux Development game** against the budgets of the graphics overhaul's second owner gate. The game plays the fight itself, so every run is the same workload; the helper only launches it, samples it and reads the numbers back.

**Budgets** (1920x1080, warm package, measured over the steady state): p95 FrameTime ≤ 16.7 ms, p95 GPUTime ≤ 12 ms, p95 GameThreadTime ≤ 4 ms, resident memory ≤ 5 GB (5120 MiB). The steady state is every frame of the measured pass outside a transition window. A budget with no measurement fails: a zero or absent GPUTime column (a driver without GPU timestamps) cannot be read as a pass. Other resolutions and `--editor` runs are reported but cannot pass the gate.

**Transition hitches are reported separately**, never inside the steady state: `start->route` (start screen to route table), `route->battle`, `battle->reward` (battle to the reward screen), and `resume` (a fresh process resuming the checkpoint). The report gives each one's worst frame, its duration and frame count, and its worst GPU and game-thread frame. `plan` (the autoplay planning on the start screen), `quit` and `reward->route` are listed too. A window runs from the frame of the click to the moment the screen has settled, and the analyzer widens each by `--transition-pad` frames (default 3).

### Running it

The gate procedure splits the work into separate locked jobs, so other workers' jobs can interleave (Shared machine, item 2):

```sh
L="flock -w 7200 /home/plebdev/.t3/ultra-unreal.lock"
# 1. Package once per commit (a Development game; see Commands).
$L python3 tools/dev.py --cores 2 package
# 2. Warm-up: creates the run folder and prints PERF_RUN <stamp>. Uses the newest finished package, or --package Builds/<stamp>.
$L python3 tools/dev.py --cores 2 perf --pass warmup
# 3. Measured pass, then the fresh-process resume, in that run folder (X is the stamp from step 2).
$L python3 tools/dev.py --cores 2 perf --pass measured --run X
$L python3 tools/dev.py --cores 2 perf --pass resume --run X
# 4. The report reads the run folder and runs no Unreal, so it needs no lock.
python3 tools/dev.py perf --pass report --run X
```

Other workers' locked jobs may run between the passes, never during one; the report lists the idle time between passes. Give every pass of one run the same `--package`/`--editor`, `--script`, `--res` and flags (and `--cores`): `resume` refuses to start if its build or flags differ from the measured pass, and the report fails if any passes disagree on commit, dirty flag, binary or flags. Each pass writes `<pass>/pass.json` (exit code, log and CSV paths, RSS, commit, dirty flag, binary, flags, start and end time). A failed pass leaves no `pass.json`; start a new run. `--pass warmup` or `--pass measured` without `--run` starts a new run; `resume` and `report` need `--run`, and `resume` needs the measured pass to have run. Without `--pass`, one invocation does all three passes and the report (up to half an hour under one lock; fine for a dry run):

```sh
flock -w 7200 /home/plebdev/.t3/ultra-unreal.lock python3 tools/dev.py --cores 2 perf
```

Each game pass holds the machine lock for its whole run (a few minutes). Run it with the window on the real display: `--offscreen` adds `-RenderOffscreen` and presents no frames. `perf` refuses a running editor for this project like `gallery` does (the report does not). `--editor` runs `UnrealEditor <project> -game` instead of a package (after a `build`) as a quick dry run of the harness; it prints the numbers but never passes. `--no-warmup` (one-shot only) skips the warm-up for a dry run; a report without a warm-up pass says so.

Three passes run at 1920x1080 (`-windowed -ForceRes`, `-novsync` so FrameTime is not pinned to the refresh rate; `--vsync` keeps it on) with `-csvCaptureFrames=<--csv-frames>` (an upper bound; the game ends the capture itself), `-csvGpuStats`, sound on (the synthesized cues are part of the game-thread cost; `--no-sound`) and `-corelimit=<--cores>`:

1. **warm-up**: a full fight, discarded, so shader and file caches are warm. It must still exit cleanly.
2. **measured**: a fresh save root, the fight, quit to the checkpoint.
3. **resume**: a new process on a copy of that checkpoint (the measured pass's save stays as the fight left it): Resume, claim the reward, take the camp, reach the route table.

A pass fails the run when the game exits non-zero or by signal, leaves a new `Saved/Crashes/crashinfo-*` (in this checkout, `~/.config/Epic/<game>/Saved`, or the staged package), does not log `AUTOPLAY_DONE ok` and a normal `LogExit`, or leaves no CSV. A game that overruns `--timeout` (or whose helper gets Ctrl-C) gets one SIGTERM and is never killed; the helper keeps waiting, and so keeps the lock, until the game has exited, printing its PID every minute and ignoring further interrupts and a closed output, then fails the pass.

One exception is retried. When the game exits by SIGFPE (exit -8 or 136), its log or console mentions SDL's `handle_wl_output_done`, and it never logged `AUTOPLAY_BEGIN`, it hit a known startup quirk of a headless Wayland output; the pass relaunches once on a fresh save. The first attempt's logs are kept as `game-attempt1.log` and `console-attempt1.log`, and `pass.json` records under `retried` its exit code and any crash reports it left. Those reports do not fail the pass; any crash report, failure or second SIGFPE from the relaunch does.

### Autoplay

`-ExpeditionAutoplay=<absolute script.json>` (`tools/autoplay/watchtower-road.json`) makes the player controller drive a real run through the same path a player uses: the build picker, the HUD buttons (`New`, `Route1`, the dock modes, `EndTurn`, `Menu`, `Resume`, `Claim`, `Camp`) and a click on a cell. It never touches rules, saves or RNG; it needs a clean `-ExpeditionSaveRoot`, and it runs only when `-ExpeditionCapture` is absent. A person at the keyboard can still interfere, so leave the window alone while it runs. `-ExpeditionAutoplayResume` runs the second pass above.

The script holds the party (the four original roles by default), the route (`dangerous`: the Watchtower road), waits (`thinkFrames`, `settleFrames`, `bootFrames`, time limits) and a list of tactical `variants`. The seed must be 20261030, the one a first New Run uses; everything else that varies is the party and the variants. Before the first click the game **plans** the fight headlessly on a detached run: for each variant a policy plays the whole encounter (a front-line hero walks up, attacks once and stands, the others use one special and hold until someone falls; then the nearest heroes walk to the fallen one and Rescue; then the party wins), and the game keeps the variant that reaches every beat (a move, an attack, a Special1 or Special2, a party member downed, that member rescued, victory) with the most survivors. If none does it logs why (`AUTOPLAY_PLAN` lines) and exits 1. The live fight replays the chosen commands at normal speed, checking before each one that the live state equals the plan's, so animation, effects and overlay are real and a divergence fails loudly. Rejected or unreachable steps, a stage that takes longer than `stageSeconds`, or a fight longer than `fightSeconds` also exit 1.

The game logs one line per beat and transition and records the same text as a CSV event, so a capture can be sliced without matching frame numbers:

```
AUTOPLAY_BEAT move frame=1234 t=41.2 step=3 type=0 actor=1 target=-1
AUTOPLAY_TRANSITION route->battle begin frame=900 t=30.1
AUTOPLAY_TRANSITION route->battle end frame=935 t=31.0 frames=35 seconds=0.9
AUTOPLAY_DONE ok pass=fresh beats=move,attack,special,downing,rescue,victory,quit steps=57
AUTOPLAY_CSV path=/home/.../Saved/Profiling/CSV/Profile(...).csv
```

(`downing` is logged when the rules commit it, which is a moment before the fall plays.) The CSV profiler writes under `Saved/Profiling/CSV`: for a packaged Linux game that is its user directory (`~/.config/Epic/<game>/Saved/...`), not the staged package. The game logs the path it wrote; the helper uses that and otherwise searches the staged package, the user directory, `~/.config/Epic/UnrealEngine/5.8/Saved/Profiling/CSV` and this checkout's `Saved/`.

### Reading the report

Everything is under `.local/perf/<timestamp>/`: `report.md` (the verdict, a budget table, the steady state, every transition, memory, the most expensive GPU passes, the warm-up and the gaps between passes, the passes and the host), `report.json` (the same data), and per pass a folder with `pass.json`, `game.log`, `console.log`, the CSV copy (`measured.csv`, `resume.csv`) and the save root used. The command exits 1 when a budget or a required transition is missing.

- **Steady state**: *gate* is every non-transition frame of the measured pass; *fight only* is the frames between `route->battle` and `battle->reward`, the heavy scene; *resume pass* is informational (calm screens, so it would flatter the gate).
- **Memory**: VmRSS of the game process from `/proc/<pid>/status` every 0.5 s, and the kernel's VmHWM high-water mark; the budget uses the larger of the sampled maximum and VmHWM, over the measured and resume passes (the warm-up is discarded).
- **Hitches**: read the worst frame and the duration of each transition; a long duration with a modest worst frame is loading spread over frames, a huge worst frame is one stall.

Limits: the numbers are for this machine, GPU and driver. GPUTime needs GPU timestamps from the RHI; if the report says no GPUTime measurement, the driver does not supply them. `-csvGpuStats` per-pass columns appear only if the RHI provides them. Planning and `quit` frames are set aside as windows, so a planning stall on the start screen never reaches the steady state. Unit tests for the analyzer, the sampler and the command are in `tools/tests/test_perf.py`; the plan and the live driver are covered by `Project.Expedition.Autoplay.` in the engine.

## Agent workflow and evidence

Use Matt Pocock skills directly under the [contribution workflow](agents/workflow.md), which owns planning, claims, review and staging delivery. Historical run reports retain their original launcher references.

Before extending the game, read the [current state note](runs/current-state.md), inspect the branch and working tree, and establish editor ownership with fresh `status`. The [V1 ledger](runs/expedition-v1/ledger.md) and later run records are delivery history. Record the feature baseline, scope, owner, validation and unresolved limits in the current run record. Keep reviewed feature PRs targeting `staging`; merging remains a separate user decision.

Establish a slice and observable acceptance criteria in the game brief or a focused design note. Inspect the tree, run doctor, and use the safe compile loop for source changes. Discover `list_toolsets`, inspect `describe_toolset`, then dispatch `call_tool` using its schema. [Editor recipes](editor-recipes.md) maps common tasks to Epic's existing tools and skills. [Architecture](architecture.md) covers C++/Blueprint and ownership conventions.

Make bounded changes using stable paths, labels, and tags. Save assets explicitly. Preserve existing user work on reruns; fail clearly when existing recipe output is incomplete. `new_level()` can save an empty map before actor creation, so map existence alone is not completion. Bootstrap validates the floor, mesh/collision, lighting, and player start, checks spawn/save results for new output, and emits its completion marker only after success. A partial existing map requires explicit repair; bootstrap does not overwrite it.

Unreal automation is selected by a narrow prefix. The project test loads the configured map, verifies a unique floor with mesh/collision, a player start, and a valid packaged default-map package. The helper requires executed passing tests in `index.json`; process exit code alone is not proof. A zero-match run fails. Passing tests are not enough either: the process lifecycle must also be clean. A non-zero exit, a signal, or a new `Saved/Crashes/crashinfo-*` report from the run is a failed lifecycle, even when every test passed (#157). It is reported alongside any test failures, and `test` and `gallery` both refuse it. Keep the crash report and any core for diagnosis. Tests render offscreen; rendered appearance is established separately by an inspected viewport capture.

PIE evidence includes identity, build, timestamp, loaded map, observed running/stopped states, and new log errors/warnings. Log scanning begins at the operation's byte offset and matches Unreal severity fields, so historical errors and messages containing the word “Error” are not misclassified. Cleanup preserves the original failure; failed cleanup reports unknown PIE state. Timed-out mutations are not automatically replayed. Inspect failure evidence before acting again.

Generated output stays ignored: editor logs in `Saved/`, operation reports in `.local/`, and packaged archives/logs in `Builds/`. Track platform resources deliberately when a product needs customization. Each automation/package run has a fresh directory. Packaging validates offscreen standalone startup and a normal quit; it does not establish packaged rendering on screen, input, performance, or another platform's SDK. A package failure leaves its logs for diagnosis. This is a Linux Development workflow, not a cross-platform abstraction.

The raw JSON-RPC escape hatch still performs exact identity verification:

```sh
python3 tools/dev.py mcp --method tools/call \
  --params '{"name":"list_toolsets","arguments":{}}'
```

Follow discovery before authoring calls. The helper sends explicit `captureTransform` and `annotations` to `CaptureViewport` because this pinned engine rejected their omission despite optional schema markings. Inspect installed plugin source when schema/runtime behavior disagrees.

## Source, assets, and connection troubleshooting

Codex project settings require trust; inspect `codex mcp list` from this directory. To change the endpoint, update `tools/versions.json`, `.codex/config.toml`, `.mcp.json`, and `DefaultEditorPerProjectUserSettings.ini` together.
