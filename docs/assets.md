# Asset provenance

Before importing or replacing assets, follow [asset intake](agents/asset-intake.md) for candidate validation and handoff. For generation, editable source preparation or revisions, follow [asset production](agents/asset-production.md) and keep a [versioned asset record](agents/asset-manifests.md) with the retained source. Record each asset's provenance here.

The sandbox uses Unreal Engine's bundled basic cube. The dark-fantasy theme and the game splash below are the only added art; both are original, agent-authored work, and nothing was downloaded.

For each imported asset or generated source, record its destination, author/provider, source URL or generation recipe, license, and modifications here. Keep editable source assets in `Art/` when introduced and import the runtime form into `Content/`.

## Dark-fantasy theme (issue #38)

The game's art set lives under `/Game/DnDDiceRoll/Theme`.

**Authorship and license:** all of it is original work by this project's agents, made with a local Blender pipeline from the owner-approved look tests (2026-11-01). No third-party art, files, names or downloads are included; in particular, nothing from the inspiration game or its reference videos. It is project-owned, with the same terms as the repository.

**Sources:** the editable sources are `Art/dark-fantasy-sources/r001/`:
- the packed Blender scenes `vigil.blend`, `root.blend` and `mission.blend`;
- `scripts/`, the Blender recipes that export each asset (`build_*.py`) plus the rogue rescale and root-tile repaint.

Each runtime mesh has a versioned record at `Art/<asset-id>/r001/asset.json`, with its glTF export beside it.

**Import:** `Content/Python/import_dark_fantasy_theme.py` imports the exports. It:
- creates `M_DiceRollTheme`, and keeps an existing master unless its stored graph revision (`MASTER_GRAPH_REVISION`, the metadata tag `DiceRollGraphRevision`) differs from the script's, and then rebuilds the graph in place (the asset and its instances survive). Set `DND_THEME_REBUILD_MASTER=1` to force a rebuild; bump the revision whenever the graph changes. See "Theme material" below;
- gives each mesh its own `MI_*` instance;
- sets textures to `TF_DEFAULT` in `TEXTUREGROUP_World`, uncompressed and sRGB. Gate 1 chose trilinear + anisotropic 8 (nearest, trilinear and sharp texels looked nearly identical at 256 texels/m). `TF_TRILINEAR` maps straight to a plain trilinear sampler, and Vulkan enables anisotropy only for anisotropic sampler filters, so `r.MaxAnisotropy=8` (`Config/DefaultEngine.ini`) would do nothing for it. `TF_DEFAULT` defers to the texture group; the engine's World group is aniso with point mips (an anisotropic-point sampler), so `Config/DefaultDeviceProfiles.ini` replaces that one group entry with aniso + linear mips, the anisotropic-linear sampler. This is a Config change (a new file) and needs coordinator approval. The filter fix reimport is expected to change only the 21 `T_*` textures (their `filter` property);
- fills `DA_DiceRollTheme`, a `UDiceRollTheme` data asset.

**Theme material (#143):** `M_DiceRollTheme` computes `base = Tex × vertex colour × Color` and adds three emissive terms, each driven by a per-instance parameter:
- `Glow` × the vertex-colour alpha mask (flames, runes, glass). There is no blanket glow share any more.
- `Fill` × a hemisphere fill (sky above, ground below, from the world normal) × the base colour, so shadowed sides keep their form.
- `Rim` × a cool Fresnel rim (exponent 3), so dark figures read against dark ground.

`Roughness` sets the surface: characters and metal 0.5 to 0.65, stone, cloth and ground 0.9 to 0.95. Characters get `Rim` and `Fill` 1; worlds and tiles get none; props a trace of `Fill`. The master is Masked: a `CameraFade` clip drops scenery nearer to the camera than `CameraFade` × the camera's height, so a diorama around the board never swallows the camera. The clip goes through a `ShadowPassSwitch` (Default: the clip, Shadow: 1), because a shadow depth pass keeps the player camera's origin and the clip would otherwise remove shadows too. `SelfLit` is a constant emissive share kept only for the flame (a light source) and the tabletop overview, which stays as it was.

**Accepted exception to gate 1's mask-only glow (decided by the lead, 2026-11-09):** the battle flame's `SelfLit` (1.4) and the tabletop overview's self-light stay. The r001 flame has no glow mask and is itself a light source. The exception lasts until r002 art with real glow masks lands (#145, #147), when both move onto `Glow` and `SelfLit` goes away.

**Vertex-alpha guard:** glTF `COLOR_0` is optional, and Unreal reads a missing vertex alpha as 1, which would make a whole mesh glow. At import the script reads each export's accessors and enables `Glow` only when `COLOR_0` is RGBA with a varying alpha. No r001 export has one (most have no `COLOR_0`; the tabletop and the two worlds have a constant alpha of 1), so every r001 instance imports with `Glow` 0 until a revised export paints a mask. The log lists `THEME_MATERIAL <mesh> glow=<n> mask=<bool>` per mesh.

**Camera clip and the occluder (#143 and #145, decision):** `M_DiceRollTheme` is masked and clips scenery closer to the camera than `CameraFade` (0.5) x the camera's height, so a diorama around the board never swallows the camera. That clip is shared code (`camera_clip()` in the import script).
- **Occluder fade (round-1 review):** the primary fade is a board test. The ray from the camera through each occluder pixel is intersected with the board-top plane; if the hit lies in the board rectangle grown by half a cell and the pixel is closer to the camera than the hit, the pixel dithers to the 15 % floor, easing back to opaque over half a cell outside the rectangle (`OccluderFade::Board` mirrors the material). The view pushes the rectangle and plane height once, and again only if they change. The camera-to-focus and camera-to-active-unit cylinders are kept because a figure at the board's far edge, seen over its shoulders, is covered by pixels whose ray lands past the rectangle, which the board test cannot see.
- **Occluder material:** it uses both, and they do not conflict. A pixel is kept only if the board and sight-line dither keep it and it is outside the camera clip (the two masks are multiplied). Near-architecture is the geometry most likely to sit around the camera, so it needs the clip too; the dither handles what blocks the view farther along the line. The clip is a hard cut with a roughly 50 cm ramp, the dither a 15 % floor, so one never fights the other: near the camera the clip wins, along the sight line beyond it the dither does.
- **World and props:** the r002 world, props, scatter and the r001 worlds keep the master's clip. For the r002 world it is harmless: the ground is always farther from the camera than 0.5 x its height, and tall architecture within that radius is removed exactly like the occluder's. It matters mainly for the r001 worlds, whose scenery surrounds the board. Mist cards and light shafts (`M_DiceRollCard`) are translucent and are not clipped.

The list and what each is for are in `Art/dark-fantasy-sources/r002/README.md`; the table that drives the import is `Content/Python/theme_plan.py` (`R002`), and `tools/tests/test_theme_plan.py` checks every row against its record, hash and package.

Import policy (v2), applied by `import_dark_fantasy_theme.py`:
- **New names, explicit replacement.** 21 assets are new packages (`SM_World_Vigil_Occluders`, `SM_Prop_*_B/_C`, `SM_Prop_Arch2Cell`, `SM_Scatter_*`, `SM_Fx_*`); an existing package is never overwritten. Four revised packages keep their recorded path and are replaced only on request: `DND_THEME_REIMPORT=world-vigil,prop-pillar,prop-wall,prop-stones` (or `all`). An id outside that allow-list is an error, and the four go together because the board scales r001 art and places r002 art unscaled (`UDiceRollTheme::bMetricKit`, set by the script only when all four carry the r002 tag).
- **Per mesh:** Nanite forced off (UE's glTF importer enables it), simple collision removed, and the package tagged `DiceRollAssetRevision=vigil-kit-r002`. **Explicit LODs for meshes over ~1k triangles; cards, light shafts and small scatter are exempt.** The world, the occluders, the nine obstacle variants, the 2-cell arch and `SM_Scatter_Roots` have `<name>_LOD1.glb` (about 50 %) and `<name>_LOD2.glb` (about 25 %, up to 40 % where the silhouette needed it) beside the export, made by `build_lods_r002.py` and listed in the asset record with their hashes and triangle counts; the script imports both, checks them against the record and fails unless the mesh ends with exactly the recorded LOD count (`lods=3`; exempt meshes `lods=1`). r001 meshes are only reported; `DND_THEME_FIX_R001_NANITE=1` switches their Nanite flag off too and changes their bytes.
- **Textures:** one atlas per mesh (the occluder repeats the world's 2048 px atlas), `TF_DEFAULT` in `TEXTUREGROUP_World` (anisotropic 8 with linear mips through `Config/DefaultDeviceProfiles.ini`, as #143), mips generated, sRGB, default compression (r001 stays uncompressed). Texture and instance settings are written only when they differ, so a rerun leaves unchanged assets byte-identical.
- **Materials:** a `MI_*` per mesh. Lit pieces use `M_DiceRollTheme` (Glow only where COLOR_0 is RGBA with varying alpha, which the r002 world, occluder and candles have). `M_DiceRollOccluder` (masked; dithered wherever it covers the board, and around the camera sight lines; parameters `BoardRect`, `BoardZ`, `BoardRamp`, `SightEye`, `SightFocus`, `SightUnit`, `FadeRadius`, `FadeMin`, plus the master's `CameraFade` clip, see below; rebuilt in place by the script when its graph lacks these parameters) and `M_DiceRollCard` (translucent, unlit, two-sided; mist cards and light shafts, opacity = COLOR_0.a) are created once and never overwritten.
- **Figure silhouettes (round-2 review):** `M_FigureSilhouette`, created once by the same script (graph revision tag `figure-silhouette-3`, rebuilt in place only when the tag differs, never overwritten otherwise), keeps figures readable behind tall kit obstacles (pillars, arches), which stay solid so blocked footprints read. It is a Post Process material at Blendable Location After Tonemapping: the fill is then the exact HUD colour, untouched by exposure, bloom, vignette and the grade (inputs and output are display space there, so the linear palette is encoded with pow(c, 1/2.2) inside the graph). It compares `SceneTexture:CustomDepth` with `SceneDepth`; where custom depth − scene depth exceeds `Tolerance` (3 cm), the figure is farther than whatever the pixel shows, so it is hidden, and the pixel mixes toward `PartyColor` (HUD Sky, stencil 1) or `EnemyColor` (HUD Danger, stencil 2, read from `SceneTexture:CustomStencil`) with that side's alpha. Visible parts and stencil 0 are unchanged. Side does not depend on colour: party is a solid, brighter fill (`PartyAlpha` 0.7, lifted 20 % toward white by `PartyLift`); enemy is diagonal hatching (screen-space stripes of x + y from `ScreenPosition` and `ViewSize`, `StripePx` 6 px at 1080p scaled by view height, alternating `EnemyStripeAlpha` 0.7 with a faint `EnemyGapAlpha` 0.15), so in greyscale a solid shape and a striped one differ. Revision 2 had the comparison reversed (it tested for a nearer custom depth) and never drew; revision 3 fixed it. It needs `r.CustomDepth=3` (`[/Script/Engine.RendererSettings]` in `Config/DefaultEngine.ini`, depth with stencil); `ExpeditionBattleView` adds it to its grade's blendables when the asset exists and sets custom depth and the stencil on every figure part (not the footprint ring); dead figures drop it. Original work by this project's agents; no third-party content.
- **Kit LOD materials (round-2 review):** each LOD glb names its own material, so `import_lod` appended a slot per LOD and LOD1 and LOD2 sections pointed at it (flat grey at default and far zoom). `repair_lod_slots` maps every section of every LOD to slot 0 (`StaticMeshEditorSubsystem.set_lod_material_slot`) and logs `THEME_LOD_SLOTS` (slots per LOD before and after). It only remaps; the extra slots stay, unused. An earlier version also trimmed them, and the first native run of that version crashed at startup, so the trim was removed (see the PR for the A/B). It runs on every kit mesh with LODs on every run, after import or when already present, and touches only meshes whose mapping is wrong, so a plain run repairs the 13 existing meshes in place (a modify, not a reimport) and leaves correct ones byte-identical.
- **Board overlay through architecture (round-2 follow-up):** `M_BoardOverlay` (from #142) now sets `disable_depth_test` (`UMaterial::bDisableDepthTest`, translucency only), so the reach contour, path ribbon, brackets, blocked crosses and footprint rings draw through pillars and arches. It carries graph revision `board-overlay-2` (`DiceRollGraphRevision`); `Content/Python/create_board_overlay_material.py` (not the theme import) rebuilds an asset with another or no tag in place, keeping the asset and its instances, and leaves a current one alone. A run changes exactly `M_BoardOverlay.uasset`. The bars are thin and translucent, so drawing over figures is acceptable; the one visible effect is a ring's near edge crossing a figure's feet.
- **Import proof (round-2 review):** `import_over` accepts a reimport only when `task.imported_object_paths` reports the expected package (`theme_plan.check_import_result`, unit-tested with stub results for a failed mesh and a failed texture import); an empty result no longer passes because the original object is still loaded.
- **Log and save:** one `THEME_ASSET` line per asset (action, source SHA-256, triangles, Nanite, LOD count, collision shapes), a `THEME_FILE` line for every Theme file whose SHA-256 changed, `THEME_FILES_CHANGED <n>`; only dirty packages are saved and a failed save raises.

## Rigged character pilot (issue #147)

`Art/rig-pilot/r001/` holds the Blender half of the rigged pilot: the shared 25-bone skeleton contract (`README.md`), the recipes (`scripts/`), checks (`metrics/`) and contact sheets (`previews/`). The fighter, wizard and raider have records at `Art/sk-hero-fighter/r001/`, `Art/sk-hero-wizard/r001/` and `Art/sk-foe-raider/r001/` (skeletal glb with nine clips, plus LOD1 and LOD2 glbs). All original, made by script in Blender 5.2.3 LTS with no third-party content; project-owned, same terms as the repository.

**Import (phase 2, done: headless import, build, automation and gallery captures are recorded on PR #164; the on-screen pass is pending):** `Content/Python/import_dark_fantasy_theme.py` imports the pilot in the same headless run as the static theme. It creates, under `/Game/DnDDiceRoll/Theme`:
- `Characters/SKEL_Humanoid`, the one skeleton, from the fighter's import;
- `Characters/SK_Hero_Fighter`, `SK_Hero_Wizard` and `SK_Foe_Raider`, each with LOD1 and LOD2 from the `_LOD1`/`_LOD2` glbs (`SkeletalMeshEditorSubsystem.import_lod`) and Nanite explicitly off;
- `Characters/Animations/A_Humanoid_<Clip>` for Idle, Walk, Melee, Ranged, Cast, Hit, Downed, Death and Recover, imported once from the fighter's LOD0 glb because every clip is shared across characters;
- `Materials/MI_SK_<name>` (an `MI_*` of `M_DiceRollTheme`: Rim 1, Fill 1, Glow only because `has_alpha_mask` sees a real vertex-alpha mask in these exports) and `Textures/T_SK_<name>` (trilinear, as the static set). The `SK_` prefix keeps them apart from the static `MI_Hero_Fighter` and `T_Hero_Fighter`.

`M_DiceRollTheme` gains `used_with_skeletal_mesh` (skinned meshes need their own shader permutation; written only when different, with a recompile only then), and `DA_DiceRollTheme` gains `FighterRig`, `WizardRig` and `RaiderRig` (`FDiceRollCharacter`: mesh, the nine clips, a yaw offset). No physics asset or collision (presentation only). The run saves only dirty packages and raises when a save fails; it logs `THEME_RIG_ASSET <kind> <path> <status>` for the skeleton, each `SK_*` mesh (with `lods=<n>`) and each clip (`imported` or `kept`), and for each data-asset property (`assigned`); each rig material instance gets the shared `THEME_MATERIAL` line, and textures get no line of their own. It ends with `THEME_RIG_COMPLETE`.

**Never overwritten, never deleted:** an existing rig asset is kept (its material and the data asset are still refreshed), and the script never deletes or replaces one. A force delete nulls the references other loaded assets hold (the theme data asset, maps, other meshes), and recreating the package does not restore them. In-place replacement (an Interchange reimport that keeps object identity) cannot be made reliable for these assets from source alone, because the shared-skeleton override pipeline and the two LOD imports are separate steps. So `THEME_RIG_REIMPORT` (comma separated: `SK_Hero_Wizard`, `SK_Foe_Raider`, `SK_Hero_Fighter`, `SKEL_Humanoid`, `animations`) only validates the whole plan first, with no side effects (known names, the whole bundle named, every source glb including LOD1 and LOD2 present), and then refuses with "delete the rig assets deliberately in the editor (fix up references), then rerun". A partial bundle left behind (some assets present, some missing) is also refused. LOD imports go through Interchange, which reports success once the import is scheduled, so the script reads the LOD count back and raises unless each mesh has 3; the `THEME_RIG_ASSET mesh` line carries `lods=<n>`.

**Pilot decisions (2026-11-09):** the three characters share one set of nine clips, including one Cast clip (revisited in #150); palette zones are skipped for the pilot; a unit hit and downed in the same step goes straight to its fall clip with no Hit first. Spells cast, whatever their normalized effect: a special with the ability's `bSpell` fact plays Cast, and so does a basic Attack that the rules reference names as a spell (`ExpeditionPose::IsSpellAttack`): the wizard's Fire Bolt at any distance and the cleric's ranged Sacred Flame. Other roles' basic attacks are weapon attacks; the remaining casters' fixed attack profiles are unnamed, so they keep weapon clips until #150 gives them rigs.

The Unreal import, build, automation and gallery captures are done (PR #164). What stays pending is the on-screen pass of the three records.

## Game splash (issue #131)

`Content/Splash/Splash.bmp` is the splash the packaged Linux game shows while it loads. It is a raw file rather than an Unreal asset: the engine reads `<Project>/Content/Splash/Splash.bmp` directly, and Linux packaging stages that exact file outside the pak (`LinuxPlatform.Automation.cs`). Non-editor builds load it with `SDL_LoadBMP`, so it is an uncompressed 24-bit BMP, 720×370 like the engine's own splash. `Content/Splash/Icon.bmp` (64×64, 24-bit) is the splash window's icon: once a splash exists, the engine also looks up `Splash/Icon` and logs `Game icon not found.` without it. Packaging stages only `Splash.bmp` by itself, so `Config/DefaultGame.ini` adds `+DirectoriesToAlwaysStageAsNonUFS=(Path="Splash")` to ship the folder. Both files are Git LFS tracked (`*.bmp`).

**Authorship and license:** original project art, made by this project's agent for the repository owner from the dark-fantasy theme above; project-owned, same terms as the repository. No third-party, downloaded or AI-image-service art.

**How it was made:** `python3 Art/splash/r001/make_splash.py` (Blender 5.2.3 LTS, ImageMagick 7.1.2):
- Blender renders the theme's own `Art/tabletop/r001/SM_Tabletop.glb` unlit (texture × baked candlelight, via `render_lib.py`) at 1440×740 → `Art/splash/r001/backdrop.png`.
- ImageMagick dims the bookshelf behind the title, adds a vignette, the gilded double frame with the corner diamonds of the in-game panels, an ornamental rule and the title "dnd-diceroll", then box-downsamples to 720×370 with no stretching → `Art/splash/r001/Splash.png` (preview) and `Content/Splash/Splash.bmp`.
- The same script draws the icon, a gold "d" monogram in the gilded frame → `Art/splash/r001/Icon.png` (preview) and `Content/Splash/Icon.bmp`.
- The title is set in Noto Serif Display Bold (SIL Open Font License 1.1, system font); only rendered letterforms are in the image, and no font file is included.
- Rebuilding: the script strips the render's metadata, so the same Blender, GPU driver and font give identical files. Another GPU or driver may shift the render's pixels slightly. On another system, point `SPLASH_FONT` at the font file (Arch package `noto-fonts`).

These are raw engine files, not `/Game/DnDDiceRoll` packages, so they have no `asset.json` record (its schema needs an Unreal package path). The editor splash is a separate image (`EdSplash`) and still uses the engine default.
